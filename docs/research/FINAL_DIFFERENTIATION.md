# 여과시간 최종 포지셔닝

> 2026-09-22 기준. 이것은 **현재 만들 제품의 범위와 특정 기존 제품 대비 확인한 방식 차이**다. 구현 성능이나 현업 수요가 입증됐다는 뜻은 아니다. 근거와 반례는 [차별화 공백 조사](./DIFFERENTIATION_GAP_RESEARCH.md), 설계 판단은 [결정안](./DIFFERENTIATION_DECISION.md)에 있다.

## 2026-09-22 갱신 — 2차 발표에서 조정한 것

아래 본문은 유지한다. 2차 발표 덱을 만들며 다음을 조정했고, PRD·실험계획에 반영했다.

- **축을 `빼기 → 담기`로 잡았다.** 기존 도구의 기본 동작은 빼기(탐지해 지우고 나머지 전송)이고, 여과시간은 업무별 **목록**을 정해 담기를 기본으로 놓는다. 실패 방향이 다르다 — 빼기는 유출, 담기는 답변 품질 저하.
- **Google SDP를 `담기 가능`으로 정정했다.** 담기가 불가능하다고 말하면 안 된다. 공식 문서가 무엇을 남길지는 호출자 몫이라고 명시하며, 비어 있는 것은 능력이 아니라 정책이다.
- **Azure Copilot Observability Agent는 덱에서 제외했다.** 내부 Azure 경로라 외부 AI 반출과 상황이 다르다. 아래 비교 기록은 유효하므로 질문이 나오면 그대로 답한다.
- **현업 인터뷰를 발표 계획에서 뺐다.** 섭외가 불확실한 것을 슬라이드에 약속하지 않기 위해서다. 검증 계획에서 삭제한 것은 아니며 보강 항목으로 남아 있다.
- **담기의 대가를 명시했다.** 업무마다 목록을 만들고 관리해야 한다. 가정은 장애 대응은 보는 정보가 반복된다는 것이고, 깨지면 담기가 성립하지 않는다.
- **용어를 `목록` 하나로 통일했다.** `Purpose package` / `필드 계약` / `패키지`를 섞어 쓰지 않는다.

## 최종 답

**여과시간의 차별화 대상은 ‘목적별 마스킹 기술’이 아니라 ‘금융 장애 로그 한 건을 AI에 반출하기 전 검토하는 업무 흐름’이다.** 사용자가 이번 장애와 업무에 필요한 필드·이벤트·관계로 만든 패키지를 보고, 무엇이 제외·변환됐는지 확인한 다음, 승인한 패키지만 등록된 AI로 전송하도록 설계한다.

다만 **독자적 알고리즘이나 업계 최초 기능은 확인되지 않았다.** 목적 기반 정책은 [XACML](https://docs.oasis-open.org/xacml/3.0/xacml-3.0-privacy-v1-spec-cs-01-en.html)에 있고, 조건부 변환은 [Google Sensitive Data Protection](https://docs.cloud.google.com/sensitive-data-protection/docs/deidentify-sensitive-data)이 제공한다. AI 경로 통제·감사·요청별 승인도 [Kong](https://developer.konghq.com/ai-gateway/ai-audit-log-reference/)과 [Databricks](https://docs.databricks.com/aws/en/ai-gateway/ai-governance) 등의 기존 기능과 겹친다. 제품을 조합해 유사한 흐름을 만들 수 있다.

## 비교 대상을 정하면 말할 수 있는 차이

[Azure Copilot Observability Agent의 공식 FAQ](https://learn.microsoft.com/en-us/azure/azure-monitor/aiops/observability-agent-governance-faq)는 모델이 볼 데이터를 리소스 scope와 RBAC로 제한하지만 **범위에 포함된 개별 telemetry table/field를 선택적으로 제외할 수 없다고 명시**한다. 여과시간은 Azure 내부 에이전트를 대체하는 제품이 아니다. **조직이 별도 AI로 결제 장애 로그를 전달하는 경로**에서 사건별 필드·이벤트·관계의 공개 범위를 전송 직전에 구성하고 검토한다는 좁은 차이가 있다. 이것은 특정 제품 방식과의 차이이지, 전체 시장에 없는 기능이라는 증거는 아니다.

## 만들 것과 증명할 것을 분리

| 구분 | 현재 상태 | 말할 수 있는 것 |
| --- | --- | --- |
| 제품 구현 | 설계 단계 | Purpose 계약에 따른 사건 패키지, 제외·변환 이유, 정책·승인, 등록 목적지 전송을 한 요청에 연결 **할 계획**이다. |
| 보안 동작 | 아직 실행 증거 없음 | 승인 뒤 내용·목적지·정책 변경, Secret 잔존, 미등록 T0, 직접 우회를 차단하는지 수신 로그로 시험 **할 계획**이다. |
| 목적별 선택의 효용 | 아직 실험 결과 없음 | 강한 공통 정책보다 공개 제한 정보를 덜 보내면서 필요한 답변 근거를 유지하는지는 **보조 실험 질문**이다. |
| 현업 필요 | 인터뷰 없음 | 실제 금융 IT 운영자와 보안 검토자가 이런 사전 검토를 필요로 하는지는 **미확인**이다. |

`왜 제외했는가` 화면은 **적용한 정책 규칙을 설명**한다. 그 필드가 실제 업무에 불필요하다는 사실까지 증명하지 않는다. Trust Tier는 위험 점수에 따라 AI를 자동 선택하지 않는다. 사용자가 등록된 목적지를 고르고 정책이 허용·검토·거부를 결정하며, T0는 항상 거부한다. [정책 명세](../spec/05_POLICY_SPEC.md)를 따른다.

## 교수님께 한 문장

> “여과시간은 새 마스킹 알고리즘이 아닙니다. 결제 장애 로그를 승인된 AI에 보내기 전에 **이번 업무에 보낼 사건 정보와 제외할 근거를 패키지로 검토하고, 승인한 내용만 전송하는 흐름**을 구현합니다. 특정 장애 AI의 리소스 단위 접근 통제와 달리 사건별 공개 범위를 전송 전에 정한다는 차이가 있지만, 기존 도구를 조합하면 유사하게 만들 수 있습니다. 그래서 실제 현업 필요와 전송·답변 결과를 검증하겠습니다.”

현업 인터뷰에서 별도 AI 반출·사전 검토 수요가 없거나 기존 설정으로 같은 절차를 충분히 수행한다면 **서비스 차별성은 성립하지 않는다**. 이 경우 목적별 마스킹을 다시 신규 기술처럼 주장하지 않고 대상 문제 또는 주제를 재선정한다.

> 문서 영향: 현재 [PRD](../spec/01_PRD.md), [실험 계획](../spec/10_EXPERIMENT_PLAN.md), 2차 발표 자료는 기존 Purpose-Aware Minimum Disclosure 가설을 중심으로 작성됐다. 위 포지션을 팀이 채택한다면 범위·우선순위·발표 문구를 그에 맞게 수정해야 한다. 이 문서 작성만으로 해당 변경이 완료된 것은 아니다.

# E2. 처음 보는 장애로 한 블라인드 시험 (2026-10-05, 예비)

## 무엇을 확인했나

파일럿의 가장 큰 한계는 "담기 목록을 장애 로그를 보고 다듬었다"였다. 목록을 만들 때 **보지 않은** 장애에서도 같은 목록(10칸)으로 원인을 찾는지 시험했다. 조건은 수집 전에 `experiments/pilot/PROTOCOL.md`에 적어 커밋했다(사전 등록, `93f91d9`).

## 방법

- 목록: `templates/incident_analysis.yaml` 그대로 동결(`28fafa9`, 10칸 = 원문 7 + 토큰화 3, 본문은 WARN 이상·5xx만). 결과를 본 뒤 고치지 않았다
- 장애: OpenTelemetry Demo 내장 스위치 중 목록 설계에 쓰지 않은 것. 모두 `emitRawPii=on`, 스위치를 켜고 확인한 뒤 180초 수집
- 전처리: 파일럿과 같은 규칙(①~⑤). 주입 흔적 규칙의 스위치 이름 목록에 새 이름 3개만 수집 전에 추가
- 조건: 그대로 · 빼기(Presidio 기본) · 담기(10칸). gpt-5.1, temperature 0, 고정 질문, 각 1회
- 결과 파일: `experiments/yeogwasigan-spring/results/20261005_232345/` (git 제외), 수집 로그: `experiments/pilot/scenarios/E2a_*`, `E2b_*` (압축본)

## 사람 채점 (2026-11-11, 박소희 1명)

**방식**

- 답 6건을 조건을 숨기고 B001~B006으로 섞어 채점했다. 조건 표(`blind_key.csv`)는 채점을 끝내고 점수를 확정한 뒤에 열었다
- 기준은 서비스와 원인이다(스위치 이름은 보지 않음). 점수 0~3:
  - 3 = 정답 서비스를 발원지로 지목하고 원인을 로그 근거로 설명
  - 2 = 서비스는 맞았으나 구체적 원인·근거가 부족
  - 1 = 증상만 말하거나 발원지를 다른 서비스로 설명
  - 0 = 무관한 서비스를 지목하거나 판단 불가
- 인용한 근거가 실제 로그에 있는지 원본에서 직접 확인했다: `GetAds Failed` 4건(답에서 든 4건과 개수 일치), `redis` 포함 줄 23건
- 점수는 `blind_answers.csv`에 입력하고 `merge`로 `results_scored.csv`에 합쳤다 (6행, 6행 모두 채점)

**채점 중 본 것**

- 감점하지 않은 경우: 원인 서비스를 맞힌 뒤 frontend가 실패를 처리하지 않았다고 덧붙인 답(B001, B002, B006), 504까지의 인과를 추론으로 이은 답(B003~B005). B006은 `GetAds`를 ad가 "다른 곳으로 거는 호출"로 오해했지만 서비스와 원인이 맞아 3점으로 두었다
- 답의 끝이 문장 중간에서 끊겨 있었다(B001 "…노출하는", B002 "…다만 다음이", B003 "…지연/중", B004 "…504 타임아웃과 Redis 오류", B005 "…이와 비슷한 패턴이", B006 "…GetAds g"). 원인은 확인하지 못했고, 출력 토큰 한도일 가능성이 있다
- 담기의 장바구니 답(B004)은 인용한 로그가 `timeUnixNano`·`severityText`·`traceId`·`spanId`·`body`뿐이었고, 그대로(B005)와 빼기(B003)의 답이 인용한 `eventName`·스택트레이스는 없었다. 담기가 에러 상세 필드를 보내지 않아서일 수 있으나 입력 파일로 확인하지 않았다(가설)

## 해석

- 목록을 다듬을 때 보지 않은 장애 2개에서도 동결된 10칸으로 원인을 찾았다. "목록이 파일럿 장애에만 맞춰졌다"는 우려에 대한 첫 반증이다.
- 다만 두 장애 모두 **에러 메시지에 원인이 직접 적힌 쉬운 유형**이다. 파일럿에서 담기가 흔들린 것은 에러 없이 느려지는 장애(S3)였다. 이번 시험은 그 어려운 유형을 다루지 못했다.
- 담기 누출이 거의 0인 것은 이번 장애의 경고·에러 줄 본문에 민감값이 섞이지 않았기 때문이기도 하다. 본문에 민감값이 섞이면 담기도 샌다(파일럿 S1, E1).
- 원인 점수는 서비스와 원인이 맞았는지만 보므로, 담기 답에서 근거가 더 적었다는 차이는 점수에 나타나지 않는다.

## 수집 중 겪은 일

- 첫 수집에서는 세 장애 모두 흔적이 없었다. 셸(zsh)이 스크립트의 인자를 나누지 않아 스위치가 켜지지 않았다. 다시 돌릴 때는 플래그 원복(`git checkout`)이 연달아 일어나며 flagd가 설정 파일 감시를 놓쳤다. 원복을 "같은 파일에 다시 쓰기"로 고치고(`11128cc`) flagd를 재시작한 뒤, 장애마다 에러가 실제로 나는지 확인하고 수집했다.
- E2c `recommendationCacheFailure`는 3분 수집 안에 추천 서비스 쪽 흔적이 보이지 않아 **주입 확인 실패로 제외**했다. 캐시가 서서히 망가져 느려지는 장애라 짧은 수집으로는 드러나지 않는다. 결과를 보고 뺀 것이 아니라 주입이 확인되지 않아 뺐고, 수집 로그는 `.실패_주입확인안됨` 폴더로 남겼다(파일럿과 같은 처리, git에는 올리지 않음).

## 한계

- 장애 2개, 각 1회, 채점자 1명(예비). 13주차 본실험(3회 반복, 채점자 2명)을 대체하지 않는다.
- 쉬운 유형(에러 메시지에 원인)만 시험했다. 에러 없는 지연형 장애로 다시 시험해야 한다.
- 6건이 모두 3점이라 조건 사이를 구분하지 못한다(천장 효과). 이번 점수는 "세 조건 모두 원인을 찾았다"는 것만 말해 주며, 차이가 없다고 말하지는 못한다.
- 정답 문장(E2a는 ad의 `GetAds` 호출 실패, E2b는 cart의 Redis 연결 실패)은 시나리오 이름과 수집 로그로 정했으며, 팀 확인을 받지 않았다. 점수 기준표는 시나리오 폴더에 `truth.yaml`이 없어 `rubric.md`에 직접 적었다.
- 답이 중간에서 끊긴 현상의 원인은 확인하지 못했다.

# 여과시간 차별화 결정안 — 사건별 AI 반출 사전검토

> 2026-09-22. **권장 피벗이며 구현·사용자 수요가 검증된 결론은 아니다.** [근거 조사](./DIFFERENTIATION_GAP_RESEARCH.md)를 먼저 읽는다. 기존 `목적별 마스킹은 답변 품질을 유지하며 공개량을 줄인다`는 주장은 핵심 차별점에서 **보조 실험 질문**으로 내린다.

## 한 문장

**여과시간은 금융 결제 장애 로그를 선택한 AI에 넘기기 전에, 해당 사건과 업무에 필요한 필드·이벤트·관계만 담은 패키지를 만들고, 무엇을 보낼지와 어떤 근거를 뺐는지를 사람이 검토한 뒤, 승인한 패키지 그대로만 전송하도록 하는 반출 게이트다.**

사용자에게 보이는 핵심 결과는 `마스킹된 글자 수`가 아니라 **전송될 사건 근거의 목록, 제외·변환 이유, 승인된 실제 전송 내용의 일치 여부**다. `INCIDENT_ANALYSIS`와 `INCIDENT_REPORT_DRAFT`는 같은 로그에서 서로 다른 패키지를 요구하는 두 사용 예시다.

**확인된 차이**는 Azure의 문서화된 `리소스 범위/권한 통제`와 이 설계의 `사건별 필드·이벤트·관계 전송 전 선택` 사이의 좁은 비교다. **시장의 모든 제품에 없는 기능**이라는 결론은 조사로 증명할 수 없다.

## 13주 범위에서 실제로 보여 줄 것

1. 합성 결제 장애 JSON 한 형식을 입력한다. 등록된 Purpose와 목적지만 선택한다.
2. 공통 Secret 제거·토큰화 후 사건별 패키지와 manifest를 만든다. Manifest에는 원본 atom ID, 선택/변환 결과, 적용 규칙 버전과 이유를 기록한다. 사람이 `보낼 정보`와 `빠진 사건 근거`를 함께 본다.
3. 정책·잔존 검사와 보안 검토를 통과한 **패키지 hash, Purpose/정책/목적지 version**에 승인을 결속한다. 실행 직전에 다시 확인한다. 변경된 패키지·목적지·정책에 이전 승인을 재사용하지 않는다.
4. 내부 처리기는 외부로 직접 연결되지 않는다. 등록된 Dispatcher만 전송하며, 수신 테스트 서버가 실제 수신 payload의 digest를 기록한다. `승인 패키지 digest = 전송 payload digest`를 검증한다. 이는 Docker PoC 증거이지 실제 금융망의 보안 인증은 아니다.

기존 [아키텍처](../spec/06_ARCHITECTURE.md), [상태·승인 설계](../spec/07_STATE_AND_ERD.md), [네트워크 테스트](../spec/09_TEST_PLAN.md)의 대부분을 재사용한다. **Dispatcher가 승인 정보와 payload hash를 독립 확인하는지**는 현재 설계에서 별도 점검이 필요하다. API에서 확인했다는 사실만으로 전송 바이트의 일치를 증명하지 않는다. 전송 증거를 지원하지 않는 실제 외부 AI에는 `우리 Dispatcher가 보낸 payload`까지만 주장하고, 외부 사업자의 내부 처리까지 증명했다고 말하지 않는다.

## 검증 계획과 중단 조건

- **제품 문제:** 금융 IT 운영자·보안 검토자에게 현재 AI 입력을 누가 고르고 누가 승인하는지, 기존 쿼리·DLP·AI Gateway 조합으로 충분한지 구체적인 최근 사례를 듣는다. 실제 사용 필요가 확인되지 않으면 서비스 차별성은 **미입증**으로 둔다.
- **기술 데모:** 정상 패키지 1회 수신, 승인 뒤 원본/패키지/Purpose/목적지/정책 변경·검사 실패·T0·직접 우회는 모두 수신 0을 재현한다. 원본 전체를 Audit에 복사하지 않는다.
- **업무 품질:** 분석과 보고서 **둘 다**에 대해 필수 사건·관계 보존과 답변 품질을 공통 패키지와 쌍으로 비교한다. 현재 [실험 계획](../spec/10_EXPERIMENT_PLAN.md)의 B 실험은 분석 한 업무 중심이므로, 두 업무의 효용 우월성을 말하려면 보고서 Gold와 paired 평가를 추가해야 한다. 일정상 불가능하면 품질 주장은 분석으로 제한한다.
- **중단/축소:** 실제 사용자가 사건별 공개 검토를 필요로 하지 않거나, 기존 설정만으로 같은 작업을 더 간단히 수행하거나, 핵심 근거가 패키지에서 사라지면 이 제품 포지션을 방어하지 않는다. 그때는 범위를 특정 도입 환경의 통합 구현·한계 연구로 축소하거나 주제를 재선정한다.

## 발표용 20초 설명

> “기존 DLP는 값을 탐지·변환하고 AI Gateway는 요청을 통제합니다. Azure의 장애 조사 AI는 공식 문서상 리소스 범위와 권한으로 모델 접근을 제한하지만, 범위 안의 개별 로그 필드를 제외할 수는 없습니다. 여과시간은 별도 AI 전달 과정에서 **이번 장애와 업무에 필요한 사건 근거만 골라 패키지를 만들고, 무엇을 제외했는지 검토한 뒤, 승인한 내용 그대로 전송됐는지 확인**합니다. 이 과정의 현업 필요성과 답변 품질은 아직 검증해야 합니다.”

## Red Team 판단

**PIVOT.** 목적별 마스킹 효과 자체를 연구 신규성으로 내세우는 방향은 선행 제품·논문과 크게 겹친다. 위 반출 사전검토 워크플로는 확인 가능한 제품 방식 차이가 있고 현재 13주 설계의 핵심 부품으로 시연 가능하다. 가장 위험한 가정은 **실제 조직이 별도 AI로 로그를 보내면서도 사건별 검토·승인을 필요로 한다는 것**이다. 현업 확인 전에는 `확실한 고객 가치`로 발표하지 않는다.

# 여과시간 주간 발표 대본 (11/4, 5분)

## 1. 받는 길을 점검하고, 칸 고르기를 시험했다

약 20초. 지난 발표 이후 한 일을 피드백 대응, 알고리즘, 결과 순서로 말씀드리고 게이트웨이를 시연하겠습니다.

## 2. AI 답이 들어오는 길도 따져야 한다

약 50초. [교수님 질문은 녹음 확인 전이라 요약으로 씀] 지난 발표 뒤 교수님께서 결과를 받아올 때 보안 문제를 물으셨습니다. 구조도를 다시 보니 나가는 길만 그려져 있었습니다. 답은 나간 길을 거꾸로 타고 들어옵니다. 지금도 밖에서 먼저 들어오는 연결은 없고, 답은 글자로만 보여 주며 실행하지 않습니다. 남은 위험은 로그에 심은 지시로 AI가 위험한 명령을 권하는 경우라, 받는 길에 응답 검사를 넣겠습니다.

## 3. 로그 칸 102개에서, 원인에 꼭 필요한 칸만 남긴다

약 40초. 칸 102개를 AI 없이 점수로 35개, 단서가 있는 4개로 줄이고, AI로 하나씩 넣어 보고 빼 봐서 최종 1칸을 더했습니다. AI를 비싼 단계에만 쓰는 깔때기입니다.

## 4. 새는 칸은 점수가 올라도 넣지 않는다

약 40초. 넷을 바꿨습니다. 점수가 올라도 민감값이 늘면 넣지 않고, 문맥 칸은 사람이 아니라 값 모양으로 찾습니다. 비용은 로컬 모델을 시험했지만 느리고 판정이 흔들려, gpt-4.1-mini로 한 번 약 0.5달러로 줄였습니다.

## 5. 다 보낸 것만큼 맞히고, 누출은 147 → 0

약 40초. 고를 때 안 쓴 장애 2개에서 다 보낸 것과 똑같이 4점을 맞히면서 섞여 나간 민감값은 147개에서 0개가 됐습니다. 다만 서비스와 시각만 보내도 4점이라 이번 검증은 너무 쉬웠고, 판정도 흔들립니다. 다음 주에 더 어려운 장애로 다시 봅니다.

## 6. 로그에 원인이 없으면, 칸을 잘 골라도 못 맞힌다

약 30초. 다른 시스템에도 그대로 돌려 봤습니다. 결과는 실패였는데, 장애 8개 모두 원인 서비스가 오류 로그를 하나도 남기지 않았습니다. 그래서 다 보내도 못 맞혔습니다. 로그에 원인이 있는지 먼저 확인하는 단계를 넣겠습니다.

## 7. 알고리즘이 고른 목록으로, 실제 장애를 분석한다

시연 약 2분. 서버는 demo 프로파일로 미리 띄워 두기(재시작하지 말 것). ① /proposals.html 에서 [목록 제안 받기] — 1단계는 실제로 계산, 넣어 보기 카드와 검증 표를 짚는다. ② 시연 전환 sec-park → [승인하고 게이트웨이에 등록]. ③ [이 목록으로 장애 분석 요청하기] → ops-kim 으로 게이트웨이, 목록이 미리 골라져 있음 → 샘플 E2a → [파생본 만들기] (107 → 6, 경고 0). ④ sec-park → [승인하고 전송]. ⑤ AI 답 'ad 서비스 UNAVAILABLE' + 받는 쪽 보안 한 줄. 라이브가 안 되면 녹화 영상.

## 8. 받는 길을 막고, 더 어려운 장애로 다시 잰다

약 20초. 다음 주에는 응답 검사를 만들고, 더 어려운 장애와 반복 측정으로 알고리즘 효과를 다시 확인하겠습니다.

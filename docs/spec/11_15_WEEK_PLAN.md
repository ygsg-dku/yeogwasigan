# 여과시간 15주 실행 계획

> **15주차가 끝나면** — 오픈소스 서비스(OpenTelemetry Demo)에 실제로 낸 장애의 텔레메트리를 여과시간이 목록대로 담아 등록된 AI로만 보내고, 원문 대비 원인 적중과 민감정보 누출을 비교한 결과를 시연·보고할 수 있다.

## 5주차 상세 분담

**목표**: 5주차 수업에 "목록에 있는 것만 보내도 AI가 원인을 찾는가"에 대한 결과표 1장과 판정을 가져간다.

**규칙**: B와 D는 장애 로그를 보기 전에 자기 작업을 커밋한다. 먼저 보면 장애에 맞춰 쓰게 되고, 실험 결과를 믿을 수 없다.

### 대운 — 로그 담당

1. 공유 폴더(드라이브)를 만든다
2. 이전 초안 `experiments/pilot/lists.json`, `scenarios.json`을 레포에서 지운다 (B·D가 새로 씀)
3. 정상 로그, 필드 이름 목록, 로그 보는 법 1장을 올린다 — span = 요청 하나의 처리 기록 / log = 서비스가 남긴 메시지 / attribute = 기록에 붙은 필드
4. D에게만 장애 6개 설명을 보낸다 (데모 플래그 설명 그대로)
5. 장애 로그 수집 — 9/23에 먼저 끝냈다(PROTOCOL v1.3, DEC-08). B·D에게는 각자 커밋을 확인한 뒤 보내고, 누구에게 언제 보냈는지 기록한다
6. 장애별 로그를 올리고, 장애마다 로그에서 어떻게 보이는지 한두 줄 적는다
7. A의 코드가 완성되면 AI 호출 24번을 실행하고 결과를 공유한다. 한 사람이 같은 계정으로 돌려야 조건이 같다

완료: 장애 로그 6개 공유 / AI 응답 24개 공유

### B — 담기 목록 담당

받는 것: 필드 이름 목록

1. 필드 이름만 보고 원인 분석용 목록을 만든다. 기준은 "장애 원인을 가려내는 데 쓰이는 필드인가". 필드마다 이유 한 줄. 카드번호·사용자 ID·주문번호·금액은 뺀다
2. 장애 로그가 올라오기 전에 `experiments/pilot/lists.json`으로 커밋한다
3. 빼기-Presidio 조건을 만든다 — 모든 텍스트 값에서 민감정보를 찾아 가린다(`.venv`에 설치됨)
4. A의 담기 코드가 목록대로 담는지 검토한다

보면 안 되는 것: 장애 로그, 이전 초안, D의 키워드
완료: 목록 커밋이 장애 수집보다 먼저 / Presidio 패키지 6개

### D — 판정·채점 담당

받는 것: 장애 6개 설명

1. 장애마다 "AI가 이 말을 하면 맞힌 것"으로 칠 키워드를 두 단계로 정한다 — 서비스 적중(어느 서비스) / 원인 적중(왜). 한국어·영어 둘 다
2. 장애 로그가 올라오기 전에 `experiments/pilot/scenarios.json`으로 커밋한다
3. AI 응답 24개를 채점한다 — A의 스크립트로 자동 채점 후 눈으로 확인
4. 결과표: 장애 6 × 조건 4마다 원인 적중 / 민감정보 누출 수 / 패키지 크기

보면 안 되는 것: 장애 로그(키워드 커밋 전까지), B의 목록
완료: 키워드 커밋이 장애 수집보다 먼저 / 결과표 1장

### A — 실험 코드 담당

받는 것: 정상 로그, 장애 로그 (지금 받아도 된다. 사건 추출 규칙은 모든 조건에 똑같이 적용된다)

1. 사건 추출 — 에러 요청, 느린 요청, 경고 이상 로그만 40건 이내. 장애 스위치 흔적과 load-generator 기록은 뺀다(PROTOCOL v1.1·v1.3)
2. 패키지 3종 — 원문 / 빼기-OTel(데모가 가려 저장한 파일에서 같은 요청) / 담기(B의 목록)
3. 민감정보 누출 세기 — 원문의 카드번호·ID 값이 각 패키지에 그대로 몇 개 남았나
4. 채점 스크립트(D의 키워드), AI 호출 스크립트(실행은 대운)

정상 로그로 먼저 완성해두고, 장애 로그가 오면 돌린다
완료: 패키지 24개 생성

### 순서

1. 대운: 정상 로그·필드 목록·장애 설명 공유
2. B 목록 커밋 / D 키워드 커밋 / A 정상 로그로 코드 시작
3. 대운: B·D 커밋 확인 → 장애 로그 공유 (수집은 9/23 완료)
4. A 패키지 24개 / B Presidio 패키지·A 코드 검토

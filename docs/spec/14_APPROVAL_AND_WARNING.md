# 14. 승인 절차와 참고 경고 기준 (v0.1)

> 작성 2026-10-10 · 담당 김준수 · 구현 `experiments/yeogwasigan-spring` 의 `gateway/WarningRules.java`, `GatewayService.java`
> 상태: **v0.1 — 팀 합의 전.** 아래 "정할 것"이 합의되면 v1.0 으로 동결하고, 그 뒤 새 장애로 다시 잰다.

## 1. 왜 필요한가

화이트리스트(담기)는 **칸 단위**로만 거른다. 허용한 칸 **안에** 섞인 값(예: 본문 속 카드번호)은 막지 못한다. 발표에서는 이 빈틈을 "사람 승인으로 보완한다"고 했지만, 무엇을 경고로 띄우고 승인자가 무엇을 보고 어떻게 판단하는지 기준이 없었다.

이전 기준(정규식 4개)으로 파일럿 S1~S6 의 담기 파생본을 재 보면 경고 398건 중 실제 민감값은 28건(7%)이었다. 나머지 370건은 Docker 사설 IP(278), 프록시 요청 ID(67), 브라우저 버전 문자열(25)이었다. 경고가 늘 뜨면 승인자는 보지 않고 누르게 된다.

## 2. 원칙

1. **반출 여부는 칸 목록이 정하고, 경고는 "사람이 봐야 하는가"만 정한다.** 경고는 파생본을 바꾸지 않는다.
2. **"높음" = 새면 바로 개인·금융 피해로 이어지고, 모양과 검증 규칙으로 확실히 알아볼 수 있는 값.** 둘 중 하나라도 약하면 "낮음".
3. **"높음"에는 오탐이 거의 없어야 한다.** 소음이 섞이면 승인이 형식이 된다.
4. **고장 나면 보내지 않는다.** 승인이 필요한 요청은 시간이 지나도 자동으로 승인하지 않는다.

## 3. 참고 경고 기준

### 3.1 검사 범위

- 화이트리스트를 거친 **파생본 전체**(모든 기록)를 칸마다 따로 검사한다. 승인 화면의 미리보기(앞 50건)와 무관하다.
- 검사하지 않는 칸: `timeUnixNano`, `observedTimeUnixNano`, `traceId`, `spanId`, `parentSpanId`, 이름에 `version` 이 들어간 칸. 숫자·16진수 모양이 민감값과 겹치기 때문이다.
- 규칙은 아래 표의 순서대로 적용하고, 먼저 잡힌 자리는 뒤 규칙이 다시 세지 않는다. 예: `user.id=<UUID>` 는 식별자 1건으로만 센다.

### 3.2 등급과 규칙

| 순서 | 종류 | 등급 | 규칙 | 근거 |
| ---: | --- | --- | --- | --- |
| 1 | 식별자 (`ID`) | 높음 | `session`·`user`·`customer`·`account`·`order`·`transaction`·`tracking` + `id` 라는 이름 바로 뒤(`=`·`:`)의 값, 6자 이상. 토큰(`TX_`·`PS_`)과 자리표시자(`{userId}`)는 제외 | PROTOCOL v1.1 민감 키. 이름이 붙은 UUID 는 실제 식별자, 이름 없는 UUID 는 요청 ID 였다(S1~S6 에서 26/26, 67/67) |
| 2 | 이메일 (`EMAIL`) | 높음 | `글자@도메인.최상위` | 개인 연락처 |
| 3 | 주민·외국인등록번호 (`RRN`) | 높음 | 생년월일 6자리(월·일 범위 검사) `-` 1~8 + 6자리 | 고유식별정보 |
| 4 | 카드번호 (`CARD`) | 높음 | 4자리씩 끊은 13~19자리 또는 붙여 쓴 13~16자리. **2~6으로 시작**(카드 브랜드 번호대) + **Luhn 검사 통과** | 1로 시작하는 13·19자리는 밀리초·나노초 시각이다 |
| 5 | 휴대폰 (`PHONE`) | 높음 | `01[016789]` + 3~4자리 + 4자리 | 개인 연락처 |
| 6 | 계좌번호 (`ACCOUNT`) | 높음 | 하이픈으로 끊은 숫자 10~14자리, 앞뒤에 글자·하이픈 없음 | 날짜(YYYY-MM-DD)는 8자리라 빠진다 |
| 7 | UUID | 낮음 | 이름 없이 나온 UUID | 요청 ID 같은 무해한 값과 모양이 같다 |
| 8 | 공인 IPv4 (`IPV4`) | 낮음 | 사설(10/8, 172.16/12, 192.168/16)·루프백·링크로컬 제외, 끝자리 0·255 제외, `/` 뒤 숫자 제외 | `HeadlessChrome/149.0.0.0` 같은 버전 문자열 오탐 제거 |

**제외(세지 않음)**: 사설 IP, 네트워크 주소·버전 문자열, 토큰화된 값, 검사하지 않는 칸.

### 3.3 승인 화면에 보이는 방식

- 요약: `높음 3 (식별자 1 · 이메일 1 · 카드번호 1) · 낮음 0`
- **높음 경고 표**: 파생본 전체에서 찾은 위치(기록 번호, 칸, 종류)와 앞뒤 문맥. 값은 가린다(`j***@example.com`, `****-****-****-7968`). 같은 칸의 다른 경고 값도 함께 가린다.
- 미리보기(앞 50건): 높음은 검게, 낮음은 점선으로 강조.

## 4. 승인 절차

### 4.1 승인 모드 (`yeogwasigan.gateway.approval-mode`, 환경변수 `YG_APPROVAL_MODE`)

| 모드 | 승인이 필요한 때 | 비고 |
| --- | --- | --- |
| `ALWAYS` (기본값) | 모든 요청 | 설계안 D5 "요청자와 승인자는 다른 사람" 그대로 |
| `CONDITIONAL` | **높음 경고가 1건 이상**일 때만 | 높음 경고가 없으면 요청자가 내용을 확인하고 **승인 없이 보낸다** |

승인 필요 여부는 요청을 만들 때 정해 저장한다(그때의 정책이 감사 기록에 남는다).

### 4.2 승인자

- 요청자가 아닌, 승인 역할(`APPROVER`)을 가진 사람. 자기 요청은 승인·반려할 수 없다.
- 승인자는 **RCA 내용이 아니라 "높음 경고가 진짜 민감값인가"**를 판단한다.

### 4.3 판단 규칙

| 상황 | 승인자가 할 일 | 시스템 |
| --- | --- | --- |
| 높음 경고가 진짜 민감값 | **반려**, 사유 필수 | 요청자가 그 구간을 빼고 다시 요청한다 |
| 높음 경고가 모두 오탐 | **"오탐 확인"** 표시 + 사유 → 승인 | 확인·사유가 없으면 승인되지 않는다(400) |
| 높음 경고 없음 | 내용 확인 후 승인 (`ALWAYS`) | `CONDITIONAL` 에서는 승인 단계가 없다 |
| "RCA 에 꼭 필요하다" | **예외 없음.** 높음 값은 보내지 않는다 | 식별자는 이미 토큰으로 관계를 추적할 수 있다 |

### 4.4 기록 (감사 기록, 추가만 가능)

| 사건 | 남는 내용 |
| --- | --- |
| `CREATED` | 레코드·필드 수, 목록 버전, **높음 경고 수, 승인 필요 여부** |
| `APPROVED` | 승인자, 지문, **오탐 확인 사유**, **요청부터 결정까지 걸린 시간** |
| `REJECTED` | 반려 사유, 걸린 시간 |
| `APPROVAL_SKIPPED` | 조건부 승인으로 승인 없이 보냄 (승인자 칸은 비움) |
| `WARNING_RECHECK_FAILED` | 승인 없이 보내기 직전 재검사에서 높음 경고가 나와 보내지 않음 |

### 4.5 고장 나면 보내지 않는다

- 승인이 필요한 요청은 시간이 지나도 자동 승인하지 않는다. 승인자 부재에 대비해 승인자를 2명 이상 지정한다.
- 승인 없이 보내기는 **요청한 사람만**, **만들 때 승인 불필요로 판정된 요청만** 가능하고, 보내기 직전에 파생본을 다시 검사한다.
- 승인 지문(파생본 해시·목록 버전·전송 대상)이 승인 뒤 달라지면 보내지 않는다(기존 규칙).

값별 시험 자료: `src/test/resources/fixtures/sensitive-values.json` (27건). 이전 기준의 알려진 오탐 2건(13자리 시각, 4단 버전)과 미탐 2건(휴대폰, 계좌)을 v0.1 에서 해결했다.

**한계**
- 규칙을 설계할 때 본 데이터(S1~S6)에서 잰 숫자다. v1.0 으로 동결한 뒤 E2·새 장애(은행 데모)로 다시 재야 한다.
- 식별자 규칙은 "ID 이름 뒤에 값이 오는" 로그 형식에 기댄다. S1 의 1건은 실험에서 넣은 형식이고, S6 의 25건은 원래 URL 에 있던 `sessionId=` 였다. 이름 없이 값만 찍는 로그는 낮음(UUID)으로 빠진다.
- 주민번호·휴대폰·계좌 규칙은 파일럿 데이터에 해당 값이 없어 시험 자료로만 검증했다.

## 6. 정할 것 (팀·현업)

1. **승인 모드 기본값**: `ALWAYS` 유지 / `CONDITIONAL` 로 전환. 권장은 `CONDITIONAL`(승인을 높음 경고에만 쓰고, 장애 대응 지연을 줄임). 바꾸면 발표의 "혼자서는 내보낼 수 없다"는 "높음 경고가 있으면 혼자서는 내보낼 수 없다"로 고친다.
2. **사설 IP**: 제외(v0.1) / 높음. 기관이 내부 주소를 반출 금지로 보면 경고가 아니라 칸 목록이나 가림으로 다룬다(경고로 두면 다시 소음 278건).
3. **식별자 높음 여부**: PROTOCOL v1.1 이 민감 키로 정했고 데이터상 구분도 깔끔해 높음을 권장.
4. **현업 확인**: "반출 금지로 보는 값은 어디까지인가" (16쪽 질문). 답에 따라 높음 목록을 고친다.

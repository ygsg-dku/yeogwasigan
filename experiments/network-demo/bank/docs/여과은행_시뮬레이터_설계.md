# 여과은행 시뮬레이터 설계

여과시간을 시연·검증하기 위한 **가상 은행**이다. 회사 서버 역할을 하며, 장애를 진짜로 일으켜 장애 로그를 만든다.
실행 방법은 [README](../README.md), 이 문서는 "어떻게 만들어졌고 왜 이렇게 구성했는가"를 적는다.

- 작성 2026-11-08 · 코드 `experiments/network-demo/bank/`
- 수치는 모두 `scenarios/BANK_*` 장애 폴더 5개(로그 1,155건)와 로컬 실측에서 뽑았다

## 1. 목적과 범위

11/4 발표 피드백: "은행 시뮬레이션처럼 시스템을 학교 서버에 두고 에러 로그를 일으켜서 시연하라."

이 시뮬레이터로 확인하려는 것은 세 가지다.

1. **네트워크 경로**: 회사 서버의 원문 로그가 네트워크로 게이트웨이까지만 가고, 외부 AI 에는 파생본만 나간다
2. **두 번째 시스템**: OTel 쇼핑몰 데모가 아닌 다른 시스템(은행)에서도 담기 · 경고 · 승인과 필드 선택 알고리즘이 같은 절차로 돈다
3. **진짜 장애**: 에러 줄을 코드로 찍는 대신, 시스템 일부를 실제로 망가뜨려서 나온 로그로 시연한다

범위 밖: 실제 금융 업무 규칙(한도·수수료·전문 형식), 실제 기관 연동, 성능·규모.

### 기존 시뮬레이터와 차이

| | OTel 샘플 (`yeogwasigan-spring/scenarios/S*`) | 카드결제 (`company/payment_service.py`) | 여과은행 (이 폴더) |
|---|---|---|---|
| 정체 | OpenTelemetry 쇼핑몰 데모에서 받아 둔 로그 파일 | 직접 만든 시뮬레이터 | 직접 만든 시뮬레이터 |
| 데이터 | 고정 | 실시간 생성 | 실시간 생성 |
| 서비스 | (원래 앱은 여러 서비스) | 프로세스 1개, 서비스 이름만 3개 | 프로세스 3개가 실제로 HTTP 호출 |
| 장애 | 원래 앱에서 장애 플래그로 일으킨 것 (다시 일으킬 수 없음) | 스위치를 켜면 코드가 ERROR 줄을 직접 씀 | 프로세스 멈춤 · DB 잠금 · 잘못된 배포로 실제 예외가 남 |

## 2. 시스템 구성

국내 은행의 **채널계 → 계정계 → 대외계** 구분을 프로세스 3개로 줄였다.

```
 가상 손님 (초당 약 3명) + 시연자 브라우저
        │
 ┌──────▼───────────┐  HTTP   ┌──────────────────┐  HTTP   ┌──────────────────┐
 │ 채널계 :9000      │ ──────▶ │ 계정계 :9100      │ ──────▶ │ 대외기관 :9200    │
 │ channel-ibk      │ 5초 제한 │ core-ledger      │ 3초 제한 │ kftc-relay       │
 │ 화면·API·가상손님  │         │ sqlite 원장(WAL)  │  타행만  │ 타행이체 중계 흉내  │
 └──────┬───────────┘         └──────┬───────────┘         └──────┬───────────┘
        │                     batch-interest (장애 ②에서만)          │
        └──────────── 같은 traceId 로 logs/bank.jsonl 에 기록 ───────┘
```

| 서비스 (`service.name`) | 실제 은행에서는 | 파일 | 버전 | 하는 일 |
|---|---|---|---|---|
| `channel-ibk` 채널계 | 인터넷뱅킹·앱 서버 | `channel.py`, `static/index.html` | 4.2.1 | 화면과 API. 가상 손님 트래픽. 처리는 계정계에 맡긴다 |
| `core-ledger` 계정계 | 원장 (계좌·잔액의 진짜 기록) | `core.py` | 5.12.0 | 조회 · 당행이체 · 타행이체. 타행이 실패하면 출금을 되돌린다 |
| `kftc-relay` 대외기관 | 다른 은행과 이체를 중계하는 바깥 기관 | `kftc_sim.py` | 3.0.8 | 타행이체를 받아 50~200ms 뒤 승인 코드 `0000` |
| `batch-interest` 배치 | 일 마감 일괄 작업 | `batch_job.py` | 1.0.3 | 이자 계산. 장애 ② 에서만 실행 |

은행 이름(여과 777 · 가람 301 · 누리 302 · 다솜 303)은 모두 가상이다. 실제 기관과 관계없다.

### 거래 흐름

| 거래 | 비율 | 흐름 | 응답 |
|---|---|---|---|
| 본인확인 | 10% | 채널계에서 끝 (세션 새로 발급) | 200 |
| 조회 | 50% | 채널계 → 계정계 `SELECT` | 200 · 404 없는 계좌 |
| 당행이체 | 25% | 채널계 → 계정계 (출금+입금 한 트랜잭션) | 200 · 422 잔액 부족 · 500 원장 오류 |
| 타행이체 | 15% | 채널계 → 계정계 (출금 기록) → 대외기관 → 완료 또는 출금 취소 | 200 · 504 대외기관 응답 없음 |
| (계정계 연결 실패) | | 채널계가 계정계를 못 부름 | 503 |

시간 제한: 채널계 → 계정계 5초, 계정계 → 대외기관 3초, 원장 잠금 대기(`busy_timeout`) 2초.
가상 손님은 손님마다 스레드를 띄운다. 한 건이 시간 초과로 묶여도 다른 손님은 계속 온다.

### 추적 번호 전파

채널계가 요청마다 traceId 를 만들고, 다음 서비스를 부를 때 `traceparent` 헤더(W3C 형식)로 넘긴다.
그래서 이체 1건이 세 서비스 로그에 이어진다. 아래는 장애 폴더에서 뽑은 실제 타행이체 1건이다 (값은 전부 가짜).

```
[channel-ibk] INFO "/api/transfer 성공 200"           spanId=917abe…
   └▶ [core-ledger] INFO "타행이체 완료"              spanId=0635da…  parentSpanId=917abe…
        └▶ [kftc-relay] INFO "타행이체 중계 완료 to=가람은행 code=0000"  spanId=696d75…  parentSpanId=0635da…
```

## 3. 데이터

### 원장 (`data/ledger.db`, sqlite, WAL 모드)

| 표 | 칸 |
|---|---|
| `accounts` | account(계좌, 키) · name · rrn · phone · balance |
| `transactions` | id · ts · kind(당행/타행) · from_acc · to_acc · to_bank · amount · status(DONE/PENDING/FAILED) · memo |

WAL 모드라서 누가 쓰기 잠금을 잡고 있어도 **읽기(조회)는 계속 된다**. 장애 ②가 '이체만 실패'가 되는 이유다.

### 가짜 사람 만들기 (`common.py`)

고정 seed(`20261108`)로 만들어서 실행할 때마다 같은 사람이 나온다. 그래서 어떤 민감값이 로그에 나올지 미리 알고, 누출을 정확히 셀 수 있다.

| 항목 | 규칙 | 예 (가짜) |
|---|---|---|
| 고객 | 50명. 성 20 × 이름 20 조합에서 뽑음 | 송지호 |
| 상대방 | 30명. 가람·누리·다솜 중 하나 | 신하준 |
| 주민번호 | 생년월일 6자리 + 성별 1 + 5자리 + **일부러 틀린 검증 숫자** → 실존 번호와 겹치지 않음 | `610524-1919…` |
| 전화 | `010-XXXX-XXXX` 무작위 | |
| 내 계좌 | `777-XX-XXXXXX` (11자리) | `777-46-807293` |
| 상대 계좌 | `30X-XXXX-XXXXXX` (13자리) | `301-6985-166926` |
| 접속 IP | 211·175·121·112 로 시작하는 무작위 | `175.80.23.83` |
| 잔액 | 200만~3,000만 원 | |

계좌 자릿수는 게이트웨이 계좌 경고 규칙(하이픈으로 끊은 10~14자리)에, 주민번호 형식은 RRN 규칙(형식만 봄)에 걸리게 맞췄다.

## 4. 로그 형식

### 3층 구조

모든 줄이 OpenTelemetry 로그 구조 `resource`(어느 서비스) / `scope`(어느 코드) / `logRecord`(무슨 일) 이다.

- 실제 업계 표준 형식이다
- 여과시간 게이트웨이 · 전송기(`shipper.py`) · 필드 선택 알고리즘이 이미 이 형식을 읽는다

```json
{"resource": {"service.name": "core-ledger", "service.version": "5.12.0", "deployment.environment": "prod-sim", "host.name": "yeogwa-company"},
 "scope": {"name": "bank.yeogwa.core.ledger"},
 "logRecord": {"timeUnixNano": "…", "severityText": "ERROR",
   "body": "타행이체 실패: 대외기관 응답 없음 (다솜은행) 3004ms (timeout=3000ms), 출금 취소 txn=878",
   "traceId": "…", "spanId": "…", "parentSpanId": "…",
   "attributes": {"txn.type": "타행", "account.number": "777-…", "peer.service": "kftc-relay", "interbank.wait_ms": 3004,
                  "exception.type": "TimeoutError", "exception.message": "timed out", "exception.stacktrace": "Traceback …"}}}
```

### 칸 이름 원칙

- **OTel 표준 이름이 있으면 그대로**: `http.route` · `http.request.method` · `http.response.status_code` · `exception.type/message/stacktrace` · `db.system` · `db.operation` · `server.address/port` · `peer.service` · `session.id` · `user_agent.original` · `error.type`
- **은행 업무 칸은 표준이 없어 직접 지음**: `txn.*` · `account.*` · `customer.*` · `counterparty.*` · `interbank.*` · `transfer.*` · `batch.*`
- 표준과 다른 것 두 개: `client.ip` (표준은 `client.address`), `duration_ms`
- **서비스마다 자기가 아는 것만 남긴다**: 채널계는 고객·세션·IP, 계정계는 계좌·잔액·DB, 대외기관은 상대 은행·상대 계좌

열 설명: **건수** = 장애 폴더 5개 1,155건 중 그 칸이 있는 기록 수 · **OTel 목록** = 기존 `INCIDENT_ANALYSIS` 가 담는 칸 · **1단계** = 필드 선택 알고리즘 1단계 판정 · **최종** = 알고리즘이 고른 은행용 목록 7칸

### 민감값을 넣은 위치와 이유

여과 효과를 재려면 걸러낼 대상이 있어야 한다. 위치는 실제로 흔한 실수를 흉내 냈다.

| 위치 | 흉내 낸 상황 | 칸 고르기로 막히나 |
|---|---|---|
| 본인확인 기록의 주민번호·전화 | 인증 결과를 통째로 로그에 남김 | 막힘 (칸을 버림) |
| 모든 채널계 요청의 실명·IP·세션 | 접속 기록 | 막힘 |
| 이체 메모 | 사람이 쓰는 자유 글. 무엇이든 들어갈 수 있음 | 막힘 |
| 계좌번호 | 같은 계좌의 거래를 잇는 데 필요 | 토큰으로 바꿔 담음 |
| **장애 ④ 디버그 덤프** | 개발자가 에러 메시지에 요청·고객 정보를 통째로 찍음 | **안 막힘** (담는 칸 `body` 안에 섞임) → 경고 규칙이 잡는다 |

## 5. 장애 4종

장애는 스위치가 아니라 **실제 원인**으로 일으킨다. 에러 줄은 파이썬이 실제로 낸 예외를 잡아서 남긴 것이다. 조작은 `bank.sh`.

| 장애 | 명령 (되돌리기) | 실제로 하는 일 | 조회 | 당행 | 타행 | 로그에 남는 단서 |
|---|---|---|---|---|---|---|
| ① 대외기관 응답 없음 | `kftc-freeze` (`kftc-resume`) | 대외기관 프로세스를 `kill -STOP` 으로 멈춤. 연결은 받아지지만 답이 없다 | 정상 | 정상 | **실패** | `TimeoutError: timed out`, "대외기관 응답 없음 3002ms", `interbank.wait_ms` 3000+ |
| ② 원장 잠금 | `batch 60` (저절로 풀림) | 이자 배치가 `BEGIN IMMEDIATE` 로 잠금을 잡고 50계좌를 처리한 뒤 한 번만 커밋 (끊어서 커밋해야 하는 실수) | 정상 | **실패** | **실패** | `sqlite3.OperationalError: database is locked`, 배치 시작 로그 |
| ③ 잘못된 배포 | `deploy-bad` (`deploy-fix`) | 계정계를 끄고 9101 포트로 다시 띄움 (설정 오타) | **실패** | **실패** | **실패** | `ConnectionRefusedError`, 계정계 시작 로그 `port=9101` |
| ④ 디버그 로그 실수 | `debug-on` 뒤 ① (`debug-off`) | 디버그 설정으로 재배포. 오류 메시지에 요청과 고객 정보를 붙인다 | ①과 같음 | | | ① + 본문에 실명·주민번호·계좌·전화 |

장애마다 '되는 것과 안 되는 것'이 다르다. AI 는 로그 패턴으로 원인을 구별해야 한다.

## 7. 테스트용으로 충분한가

**충분한 점**

- 장애가 진짜다. 실제로 기다리다 시간 초과가 나고, 실제 예외와 스택트레이스가 남는다. 대기 시간도 실제로 잰 값이다
- 장애마다 증상 패턴이 달라 원인 판별에 의미가 있다
- 정답(원인 · 민감값 전체)을 알아서 누출을 정확히 셀 수 있다. 실제 운영 로그로는 불가능한 측정이다
- 같은 조건으로 언제든 다시 만들 수 있다 (고정 seed, `make_scenarios.py`)
- 민감값이 칸에 있는 경우 · 자유 글 · 담는 칸 안에 섞이는 경우를 모두 포함한다

**한계**

| 한계 | 영향 |
|---|---|
| 세 서비스가 같은 형식 · 같은 이름 규칙 | 실제 은행은 팀마다 칸 이름이 다르고 텍스트 로그 · 고정 길이 전문이 섞인다. 형식이 뒤섞인 로그에서 알고리즘이 통하는지는 검증하지 못한다 |
| 서비스 3개 · 업무 3종 · 장애 4개 | 실제 시스템의 규모와 잡음(재시도 · 연쇄 장애 · 대량 배치 로그)이 없다 |
| 만든 사람이 정답을 앎 | 에러 메시지가 원인을 친절하게 말한다 ("대외기관 응답 없음"). 실제 장애는 더 애매하다 |
| 장애마다 1회 수집 · 채점 1회 | 점수가 흔들린다 (위 `body` 가 빠진 일) |
| 실명 생성 규칙이 단순 (400개 조합) | 이름 탐지 실험에는 부족하다 |

정리: **캡스톤 시연과 "두 번째 시스템에서도 같은 절차가 돈다"를 확인하는 용도로는 충분하다.
"실제 은행 로그에서 통한다"는 증거로는 부족하다** — 발표에서 한계로 밝힌다.

**보강안**

- 대외기관만 다른 칸 이름이나 텍스트 형식으로 쓰게 해서 '형식이 섞인 로그'를 흉내 낸다
- 장애마다 seed 를 바꿔 여러 번 수집하고 점수를 평균 낸다
- 재시도 · 연쇄 장애 같은 잡음 로그를 추가한다

## 8. 개인정보 처리

- 고객 · 상대방 · 계좌 · 전화 · IP 는 모두 가짜다. 주민번호는 검증 숫자를 일부러 틀리게 만든다
- `host.name` 은 실제 컴퓨터 이름 대신 `yeogwa-company` 로 쓴다 (컴퓨터 이름에 개인 이름이 들어 있을 수 있음)
- 장애 폴더를 저장할 때 스택트레이스 속 내 컴퓨터 경로를 학교 VM 경로(`/home/ubuntu/yeogwasigan/…`)로 바꾼다
- 필드 탐색 2·3단계는 후보 칸을 실제로 AI 에 보내므로 이 가짜 데이터로만 돌린다 (10/27 결정)
